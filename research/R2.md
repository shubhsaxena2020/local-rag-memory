The worker report was not promoted because it contained unsupported numerical pass thresholds, an incorrect RAGTruth join field, a mistaken LongMemEval stratification, and overconfident data-rights conclusions. ## Scope and comparison rules

Evaluation assets below fall into two groups. LongMemEval, LoCoMo, BEIR/MTEB task datasets, RAGTruth, HaluEval, FaithBench, and FACTS Grounding provide benchmark examples or labels. RAGAS and ARES provide evaluation methods and software; they do not supply one canonical benchmark dataset for this project.

Keep metrics within their measurement target. Retrieval nDCG/Recall/MRR do not measure generation correctness. Faithfulness against retrieved text does not measure whether the text itself is correct. Lexical overlap does not equal semantic correctness. Detector accuracy on intentionally constructed cases does not estimate a generator's natural hallucination rate.

For every answer-quality comparison, freeze the exact answerer model and generation settings across all compared conditions. Record the answerer ID, provider, temperature, prompt/version, condition, retrieved context IDs, and latency for each row. Keep the judge separately identified and fixed within a comparison. A changed model or prompt starts a new comparison; do not pool the rows. These controls are required by this project, not supplied automatically by the external benchmarks.

No benchmark-specific pass threshold is inferred here. Apply only the pre-registered PRD gates for project claims; treat any exploratory threshold as TEST until registered and evaluated on held-out data.

## Benchmark and framework profiles

### LongMemEval — interactive long-term memory dataset

- Primary sources: paper/repository at https://github.com/xiaowu0162/LongMemEval and https://arxiv.org/abs/2410.10813; cleaned dataset at https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned.
- Released October 2024; accepted at ICLR 2025. The authors announced cleaned history in September 2025.
- 500 questions cover single-session user facts, single-session assistant facts, single-session preferences, multi-session reasoning, temporal reasoning, and knowledge updates. A question ID ending `_abs` denotes an abstention item; abstention is an overlapping marker, not a disjoint seventh question type.
- Files: `longmemeval_s_cleaned.json` (about 115k tokens/about 40 sessions per instance), `longmemeval_m_cleaned.json` (about 500 sessions), and `longmemeval_oracle.json` (evidence sessions only). All have 500 instances. The benchmark also exposes session evidence IDs and turn-level `has_answer` labels.
- The Hugging Face dataset card declares MIT. The source repository has an MIT code license. These are distinct declarations; inspect the dataset card and terms for the specific downloaded revision before use. The broader custom-history materials reference ShareGPT and UltraChat filler data; rights for separately sourced components are not inferred from the repository code license.
- Feasible plan: first run the 500-item oracle set for QA scoring; then use a preregistered stratified sample from S that covers all six question types and includes abstention IDs, reporting exact counts by type and abstention marker. Do not describe abstention as a mutually exclusive type.
- The official evaluator `src/evaluation/evaluate_qa.py` documents GPT-4o in its example. Using another judge is a local protocol variant, not the official reported score. The official repository documents a Python 3.9 environment; full reproduction scripts assume Linux/CUDA, while evaluation-only dependencies are smaller. Windows support is not established by that documentation.
- Score generated hypotheses with the official task-aware QA evaluator; report overall and per-type accuracy, including abstention. Retrieval recall is a separate measurement. The paper's retrieval protocol excludes its 30 abstention instances because they lack evidence locations.
- Limits: generated, attribute-controlled histories differ from natural user logs; an offline batch does not fully test online ingestion or lifecycle behavior. Oracle context is not a realistic retrieval condition.

### LoCoMo — long-conversation memory dataset

- Primary sources: https://arxiv.org/abs/2402.17753 and https://github.com/snap-research/locomo (data file `data/locomo10.json`, license file `LICENSE.txt`).
- Released February 2024; ACL 2024. The current repo contains ten conversations, a subset of the initial 50-conversation release. Each has QA and event-summary annotations; the dialogue also supports a multimodal dialogue generation task.
- Data includes chronologically timestamped sessions, two speakers, dialogue IDs, QA categories/evidence IDs, generated observations and session summaries, annotated event summaries, and image URLs/captions. The images themselves are not released and external URLs can fail.
- The repository's data license is CC BY-NC 4.0. Treat it as non-commercial; do not use it for a commercial product or training without separate rights review.
- Feasible plan: use a single conversation only for a smoke check; report the conversation and question counts actually evaluated. For a benchmark result, use the full released ten-conversation subset and the official evaluation scripts. Do not claim a 50-conversation reproduction from the current `locomo10.json` file.
- Run the released scorer and report its metric names and task/category breakdown. Do not silently substitute token EM/ROUGE/BERTScore for an LLM-judge protocol or compare those metrics as if they were interchangeable. Exact local scorer version and model settings must be recorded.
- Resource needs depend on the answerer, judge, and context path. Local deterministic lexical metrics need CPU; LLM-judge evaluation needs the declared API or local inference endpoint. The dataset repository does not establish a universal hardware/runtime figure.
- Limits: only ten conversations in the current release, machine-generated dialogue, external image links, and scorer/model dependence. It is not a clean test of online fact extraction or multi-user isolation.

### MTEB / BEIR — embedding evaluation suite and retrieval datasets

- Primary sources: BEIR paper/repository at https://arxiv.org/abs/2104.08663 and https://github.com/beir-cellar/beir; MTEB paper/repository at https://arxiv.org/abs/2210.07316 and https://github.com/embeddings-benchmark/mteb. Dataset pages include https://huggingface.co/datasets/mteb/SciFact and the corresponding NFCorpus task card.
- BEIR (2021) is a heterogeneous zero-shot IR benchmark suite; MTEB (2022; EACL 2023) evaluates embedding models across multiple task types. Neither is one dataset with one license. Each selected task corpus has its own provenance and terms. Record task revision and license before acquisition; do not infer data rights from either software repository's Apache-2.0 license.
- SciFact and NFCorpus are small compared with MS MARCO; commonly listed corpus/query counts are task-revision dependent and must be confirmed from the exact task card/config loaded for a run. Do not claim a fixed runtime without measuring the chosen model and hardware.
- Feasible plan: use SciFact and NFCorpus as retrieval-only probes after confirming their dataset revisions and terms; load their standard corpus, query, and qrels splits through the pinned MTEB/BEIR version. Downloaded datasets and model weights may have separate terms.
- Run the task's official evaluator and report nDCG@10, Recall@k, MRR/MAP only where provided. Record model ID/revision, query/document formatting, truncation, normalization, backend, device, batch size, and timing method.
- Model inference may use CPU or accelerator; RAM/runtime depend on model size, precision, batch size, and corpus. `faiss-cpu` is one possible IR dependency, not a universal MTEB requirement.
- Limits: measures ranking against each task's qrels, not the project's answer generation, temporal updates, abstention, or claim grounding. Results across different tasks are not one scalar quality claim.

### RAGAS — evaluation framework

- Primary sources: paper https://arxiv.org/abs/2309.15217; current project https://github.com/vibrantlabsai/ragas and documentation https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/.
- First paper: September 2023. Current software and metrics evolve; pin the release and metric implementation used. Apache-2.0 applies to framework code, not to user-supplied examples or generated data.
- RAGAS supplies metrics such as faithfulness, context precision/recall, and response relevancy. It is not a canonical fixed dataset; this project must supply its own inputs/references. Metric column requirements differ.
- Feasible plan: use 20–50 manually reviewed project examples as a metric pilot, then compare score behavior with human claim-level judgments before using it as a gate. This is an experiment size, not a source-reported guarantee.
- LLM-based metrics require the declared judge model; some metrics also require an embedding model. Record exact versions, model IDs, prompt configuration, and per-row judge output. The current docs do not establish a fixed local hardware requirement.
- Faithfulness assesses whether answer claims follow from retrieved context. It does not establish that the context is correct, and its score is not automatically a binary hallucination label or calibrated probability.
- Limits: evaluator and prompt dependence, metric-specific assumptions, and possible judge disagreement. Do not convert a score to a pass threshold without held-out human validation and preregistration.

### ARES — evaluation framework

- Primary sources: paper https://arxiv.org/abs/2311.09476; implementation and current requirements https://github.com/stanford-futuredata/ARES.
- Paper: November 2023. ARES evaluates context relevance, answer faithfulness, and answer relevance through synthetic examples, fine-tuned judges, and Prediction-Powered Inference (PPI).
- It is a framework, not a fixed benchmark dataset. The current README requires a human-labeled validation set of at least 50 query/document/answer examples, few-shot examples, and a larger unlabeled evaluation set; several hundred validation examples are described as ideal. The repository provides Natural Questions example files, but those files' provenance/license must be checked separately.
- Feasible plan: defer unless the project can curate validation labels and version-compatible model dependencies. If piloted, report the labeled set design, prompt/model, unlabeled sample, classifier, and PPI interval.
- The README documents hosted LLM API examples and classifier-based options. Hardware and latency vary by model/config; do not generalize a single GPU requirement.
- Limits: domain-distribution dependence, human label cost, synthetic generation artifacts, and PPI assumptions. Its PPI estimates are not directly comparable to uncalibrated RAGAS or raw LLM-judge scores.

### RAGTruth — human-annotated RAG response dataset

- Primary sources: paper https://arxiv.org/abs/2401.00396 and repository https://github.com/ParticleMedia/RAGTruth, especially `dataset/response.jsonl` and `dataset/source_info.jsonl`.
- Released January 2024; ACL 2024. Nearly 18,000 generated responses have manual response-level and word/span-level labels for QA, Data2txt, and Summary tasks. `response.jsonl` has `split` (`train`/`test`), response/model/labels, and `source_id`. `task_type` is in `source_info.jsonl`, keyed by `source_id`; filter QA by joining these files, not by searching for `task_type` in `response.jsonl`.
- GitHub identifies the repository license as MIT. That alone does not settle all rights for the embedded MS MARCO, Yelp, and CNN/DailyMail source material. The upstream dataset rights for the chosen records remain UNKNOWN until individually verified. Do not claim the full corpus is an unrestricted MIT data asset.
- Feasible plan: after the join, use a preregistered sample of QA test responses only; preserve response-level split and record filtering/exclusion counts. Do not use the test split for calibration.
- Score word/span detection and response-level hallucination detection separately with precision/recall/F1 and PR-AUC where class imbalance warrants it. A judge's continuous score must be validated against the labels; RAGAS faithfulness is not interchangeable with these annotations.
- CPU is sufficient for label aggregation. A detector or judge adds model/API requirements; report them. Limits: fixed generated responses and source corpora, label taxonomy, task-specific distributions, and no measurement of retrieval quality.

### HaluEval — mixed human-annotated and generated detection dataset

- Primary sources: paper https://arxiv.org/abs/2305.11747 and https://github.com/RUCAIBox/HaluEval.
- Paper/repo: 2023. Repository describes 35K examples: 10K each for QA, knowledge-grounded dialogue, and summarization, plus 5K general user-query responses with human hallucination labels. Task-specific generated hallucinations were constructed from HotpotQA, OpenDialKG, and CNN/DailyMail seeds; general queries use Alpaca-derived prompts and ChatGPT responses.
- Repository declares MIT for HaluEval materials. Because the data embeds or derives from named external corpora, verify the rights of each source before commercial reuse; the repository metadata alone does not establish those upstream permissions. Exact terms for all underlying components: UNKNOWN here.
- Feasible plan: use a task-specific, preregistered diagnostic subset and keep source/case type in results. Do not manufacture a balanced subset unless the source provides labels and the sampling rule is fixed before evaluation.
- Use the released labels and the benchmark's documented detector evaluation, reporting accuracy, precision, recall, and F1 with class counts. Freeze the tested detector/judge prompt and model.
- CPU suffices for data handling; inference requirements depend on the tested model/API. Limits: constructed hallucinations and detection ability do not estimate natural answer-generation error rates.

### FaithBench — human-annotated summarization hallucination dataset

- Primary sources: NAACL 2025 paper https://aclanthology.org/2025.naacl-short.38/ and https://github.com/vectara/FaithBench.
- Paper: 2025. Released files are batches 1–16 except batch 13. Each example has a source, summary, annotations/spans, and metadata. Cases were selected for disagreement among detectors; the set intentionally overrepresents difficult cases.
- The repository's LICENSE is CC BY-NC-SA 4.0. Non-commercial and share-alike restrictions apply to dataset use; review the exact license before redistribution or commercial use.
- Feasible plan: one released batch can be used for a pilot after counting its examples from the actual file; exact per-batch size is not asserted here. Keep batches intact or document a fixed sample.
- Aggregate annotations using the repository's `scripts/binarize.py` only for a binary task; retain the original taxonomy and span labels for detailed analysis. Report precision/recall/F1 and class balance. Model/API needs depend on the tested detector.
- Limits: summarization-only, detector-disagreement selection, and nonrepresentative prevalence. Its accuracy is not directly comparable to an unfiltered dataset.

### FACTS Grounding — long-form grounding benchmark and leaderboard

- Primary sources: paper https://arxiv.org/abs/2501.03200, HTML https://arxiv.org/html/2501.03200, announcement https://deepmind.google/blog/facts-grounding-a-new-benchmark-for-evaluating-the-factuality-of-large-language-models/, and Kaggle benchmark/data pages https://www.kaggle.com/benchmarks/google/facts-grounding and https://www.kaggle.com/datasets/deepmind/facts-grounding-examples.
- Paper v1: January 6, 2025. 860 public Open examples and 859 private Blind examples; human-written requests and context documents; context length up to 32k tokens, mean around 2.5k. Tasks include QA, summarization, and rewriting across finance, technology, retail, medical, and legal domains.
- The paper is CC BY 4.0. The Kaggle dataset page's separate data license is UNKNOWN in this review; do not infer it from the paper license. Private examples are not locally available.
- Feasible plan: public Open subset only, selected by preregistered context-length bands and task/domain strata. The paper's full leaderboard protocol uses LLM judges for eligibility and grounding; three judge families (Gemini 1.5 Pro, GPT-4o, Claude 3.5 Sonnet) are aggregated for the published score. A single local judge is a different protocol and must be labeled so.
- Compute/API costs scale with context and judge count. No local hardware/runtime promise is made. Record exact public data revision, prompt, response model, judge model/template, and aggregation rule.
- Limits: public/private split mismatch, possible pretraining exposure of web documents, long-form domain/task distribution, and judge dependence. Do not treat the paper's published leaderboard number as a local result.

## Feasible project evaluation plan

1. Keep the existing 165-query project golden set and 40 no-answer probes as the primary held-out project measure. Do not replace its strict relevance rule with external benchmark scoring.
2. For retrieval-only embedding comparisons, pilot SciFact/NFCorpus only after task-revision and data-term verification. Keep model and formatting fixed within each run; report the task metrics separately.
3. For memory reasoning, run LongMemEval oracle for a full benchmark score if resources permit, and a separately labeled S-set stratified sample. Evaluate both retrieval and answer generation as separate outcomes.
4. For hallucination detection, consider a held-out RAGTruth QA subset only after joining `response.jsonl` to `source_info.jsonl`; use test labels once. Use FaithBench as a separate hard-case diagnostic, not a prevalence estimate.
5. Use RAGAS or ARES only as a judge/framework pilot. Validate the metric against human labels before setting an acceptance threshold. Do not compare raw scores across judge models or frameworks.
6. Do not download/use LoCoMo, HaluEval, FaithBench, or FACTS data for commercial training or redistribution based on this report. Verify exact upstream terms first; LoCoMo and FaithBench are explicitly non-commercial, and FACTS Kaggle data rights remain UNKNOWN.
7. Do not publish external benchmark results as project gates unless the dataset revision, protocol, answerer/judge IDs, and threshold were preregistered before the run.
