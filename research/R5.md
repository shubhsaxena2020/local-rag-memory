# R5 - Vector search at laptop scale (sqlite-vec flat vs hnswlib vs usearch vs faiss-cpu vs DiskANN-style)

Date of research: 2026-10-19 (IST). Round 3 restart, package attempt 1. Lane R5 from docs/PLAN-24H.md (line 120).
Target machine per docs/PRD.md: Windows 11, Core Ultra 5 225H, 48 GB RAM. Project targets (PLAN-24H.md): warm retrieval p50/p95 < 150/400 ms
(stretch < 60/150 ms), whole-system RAM < 2 GB (stretch < 1.2 GB), expected realistic corpus < 50k facts (PLAN E6).

## 0. How this was produced, and what is NOT in here
- API-only. No local benchmark was run, no project code/config/data was edited, no eval output/report/sealed content was read.
  Project docs read only for lane definition and targets: PLAN-24H.md, PRD.md, ARCHITECTURE.md.
- The built-in web_search/web_extract providers were NOT configured in this session ("No web search provider configured"). I therefore fetched
  primary URLs directly (PyPI JSON API, GitHub API/raw files, vendor blog pages, arXiv PDFs) over HTTP. Discovery was by known-source, not by search
  engine, so a relevant third-party benchmark may be missing. This is a coverage limitation.
- Every "MEASURED" row below is a number a primary source printed, with its own hardware. "ESTIMATE" rows are my arithmetic and are labelled.
  There is NO source that measured these libraries on Windows / Core Ultra 5 225H / Python 3.13 at 10k/100k/1M facts. So no latency table for this machine exists yet.

## 1. Bottom line
1. At the expected corpus (<= 50k facts, <= 100k worst case) an exact (flat/brute-force) scan is the right design. ESTIMATE: tens of ms or less per query
   (section 5), inside the 150 ms p95 stretch target, with 100% recall by construction and no index to rebuild when facts are superseded.
2. sqlite-vec (flat, in the same SQLite file as facts + FTS5) is the best fit: one 0.29 MB pure-C wheel with a Windows build, transactional with the fact
   store, supports float32/int8/bit. Risks: pre-v1 (README says expect breaking changes), last stable release 0.1.9 on 2026-03-31, only alphas since.
3. ANN (HNSW) only pays off around 500k-1M+ facts of float vectors, which is 10-20x beyond the plan's expectation. Do not build it now.
4. DiskANN is a billion-scale, SSD-resident design. diskannpy has no Python 3.12/3.13 wheel at all. Reject for this project.
5. Binary/int8 quantization with float rescoring is the first lever to pull if flat ever gets slow, before any graph index.

## 4. ESTIMATE: memory (pure arithmetic, vectors only, MiB = 2^20 bytes)
Formula: float32 = N*d*4; int8 = N*d; bit = N*d/8. HNSW (hnswlib source, hnswalg.h lines 126-129): per element = (2M*4+4) link bytes + d*4 + 8 label bytes at level 0, plus upper levels
~N/M elements * (M*4+4). M=16. FAISS HNSWFlat per its wiki: d*4 + M*2*4 bytes per vector (same order). usearch graph overhead not derived (not measured).
| Facts N | d | float32 | int8 | bit | hnswlib f32 (M=16) |
| 10,000 | 384 / 768 / 1024 | 14.6 / 29.3 / 39.1 | 3.7 / 7.3 / 9.8 | 0.46 / 0.92 / 1.22 | 16.0 / 30.6 / 40.4 |
| 50,000 | 384 / 768 / 1024 | 73.2 / 146.5 / 195.3 | 18.3 / 36.6 / 48.8 | 2.3 / 4.6 / 6.1 | ~80 / ~153 / ~202 |
| 100,000 | 384 / 768 / 1024 | 146.5 / 293.0 / 390.6 | 36.6 / 73.2 / 97.7 | 4.6 / 9.2 / 12.2 | 159.8 / 306.3 / 404.0 (+0.4 upper) |
| 1,000,000 | 384 / 768 / 1024 | 1464.8 / 2929.7 / 3906.2 | 366 / 732 / 977 | 45.8 / 91.6 / 122 | 1598 / 3063 / 4040 (+4 upper) |
- Reading: at 100k x 768 float32 the whole vector set is ~0.29 GiB, well inside the 2 GB whole-system budget. At 1M x 768 float32 (2.9 GiB) it is NOT, so 1M requires int8
  (0.72 GiB) or bit (0.09 GiB) + float rescore from disk. hnswlib stores float32 only (no quantization option in its API), so it cannot meet <2 GB at 1M x 768.
  usearch (f16/bf16/i8/b1) and faiss (SQ8/PQ/RaBitQ) can. Multi-vector-per-fact (e.g. contextual variants) multiplies all numbers.

## 5. ESTIMATE: single-query latency of exact scan (bandwidth model, NOT measured on this machine)
Model: time = bytes_scanned / effective_bandwidth. Effective bandwidths DERIVED from measured M1-M4: 4.0 GB/s (vec0 1M x 192 float, on-disk, 768 MB/0.192 s),
15.5 GB/s (vec0 sift1m, 512 MB/33 ms), 30 GB/s (static sift1m, 512 MB/17 ms), 46.8 GB/s (static GIST 1.92 GB/41 ms). All on an M1 mini, so the 225H may be higher or lower.
| N x 768 f32 | bytes | @4 GB/s (pessimistic) | @15 GB/s (mid) | @47 GB/s (optimistic) |
| 10,000 | 30.7 MB | 7.7 ms | 2.0 ms | 0.7 ms |
| 50,000 | 153.6 MB | 38 ms | 10 ms | 3.3 ms |
| 100,000 | 307 MB | 77 ms | 20 ms | 6.5 ms |
| 1,000,000 | 3.07 GB | 768 ms | 205 ms | 65 ms |
| 1,000,000 int8 | 768 MB | 192 ms | 51 ms | 16 ms |
| 1,000,000 bit (+ rescore of k*oversample float rows) | 96 MB | 24 ms | 6 ms | 2 ms (+ rescore cost, not modelled) |
- Excludes SQLite/Python/JSON overhead, top-k selection, and the query embedding itself (which for Ollama will dwarf the scan). These are planning bounds, not results.
- HNSW query latency cannot be estimated honestly without recall: it depends on ef, M and data. M5 shows nmslib-HNSW is ~100x faster than exact at 1-R@1 0.82 on SIFT1M
  (batch, 20 threads, 2018 CPU); no primary source gives HNSW ms/query for 768-d text embeddings at our N on Windows. Left as "to measure".

## 6. Option-by-option assessment
- sqlite-vec flat (vec0): + same file/transaction/WAL as facts, DELETE/UPDATE supported, metadata/partition/auxiliary columns allow filtering (e.g. active-fact flag) in the KNN WHERE
  (https://alexgarcia.xyz/sqlite-vec/features/vec0.html); + int8/bit types and vec_quantize_binary; + alpha ANN: rescore (bit/int8 coarse + float rescoring, oversample),
  experimental IVF (compile flag), DiskANN (PR #276/#277/#278, released in v0.1.10-alpha.1 on 2026-03-31). - pre-v1, alphas only since March; author documents DiskANN inserts as
  "VERY slow" and DELETEs expensive (alpha.2 notes); metadata-column scans are "slower full scan"; one maintainer, 216 open issues (GitHub API 2026-10-19). Brute force only in stable.
- hnswlib: + simplest HNSW, incremental add, mark_deleted/replace, filter callback, thread-safe adds; - no PyPI wheel on Windows for 3.13, last PyPI release 2023-12-03, float32 only,
  Python filter path slow in multithreaded mode (README), index kept in RAM and rebuilt/saved separately from SQLite (two sources of truth).
- usearch: + tiny wheel with Windows amd64/arm64 cp313, f16/bf16/i8/b1 dtypes, `view=True` memory-mapped serving from disk, exact=True brute-force mode, very active releases (3 in 17 days).
  - fast release cadence = API churn risk; vendor-only comparative claims; index file separate from SQLite.
- faiss-cpu: + reference implementation, Flat/IVF/HNSW/PQ/SQ/RaBitQ, official Windows cp313 wheel; best tool for computing exact ground truth. - 16 MB wheel with OpenMP/BLAS,
  HNSW "does not support removing vectors" and sequential adds only (use IDMap), all indexes in RAM per its wiki guidance page
  (https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index). Its own guidance: "few searches -> Flat; below 1M IVF with K=4*sqrt(N)..16*sqrt(N); HNSW if lots of RAM".
- DiskANN-style: original DiskANN (M6) needs SSD + PQ in RAM and targets 10^9 points; diskannpy dead for 3.12+/3.13; the new DiskANN3 repo is a Rust library with providers (no Python package
  found in the repo root listing; I did not search crates/PyPI exhaustively). The only DiskANN-style piece realistically usable here is sqlite-vec's alpha `indexed by diskann(...)`
  (LM-DiskANN-based; binary neighbor quantizer; params n_neighbors, search_list_size_insert/search), which the author flags as slow to build and growing slower with size.

## 7. Recommendation by corpus size and resource constraints
| Facts | RAM budget | Recommendation | Basis |
| <= 10k | any | sqlite-vec flat, float32 (or NumPy fallback already planned) | ESTIMATE < 8 ms even at pessimistic bandwidth; 30-40 MiB |
| 10k-100k | < 2 GB | sqlite-vec flat float32; consider int8 only if p95 vector stage > ~40 ms | ESTIMATE 20 ms mid, 77 ms pessimistic at 100k x 768; 0.29 GiB |
| 100k-500k | < 2 GB | sqlite-vec flat with bit/int8 coarse + float rescore (rescore index alpha or manual two-column pattern); measure recall loss on OUR embedder | M7 shows loss is model-dependent (74.8% to 96.5%) |
| 500k-1M+ | < 2 GB | quantized flat first; then usearch HNSW with i8/f16 (view=True) or sqlite-vec DiskANN alpha, only if the measured flat p95 exceeds budget | graph ANN has hard-to-bound recall loss and a second persistence layer |
| > 1M or > RAM | n/a | out of scope for a single-laptop memory service | DiskANN (M6) territory |
Constraint rule: with whole-system RAM < 2 GB and an embedding model resident elsewhere, keep vector bytes under ~0.5 GiB: that is 100k x 1024 f32, 170k x 768 f32, or 700k x 768 int8.

## 8. Runnable measurement plan (E6), to execute later; nothing was run here
1. Environment capture: Python version, `sqlite3.sqlite_version`, enable_load_extension smoke test, `pip install sqlite-vec usearch faiss-cpu` in a clean venv (3.13), time + wheel sizes; try `pip install hnswlib` and record whether MSVC build succeeds; record failures verbatim.
2. Data: real embeddings from the chosen embedder (E5 winner) for >= 20k real facts + public text for scale-up (NOT tiled-with-noise copies for recall tests: tiling creates near-duplicate clusters that make ANN recall look better than real data; use tiling only for pure latency/RAM at 500k-1M).
   N in {10k, 50k, 100k, 500k, 1M}; d from the winning model (and 256 after Matryoshka truncation).
3. Ground truth: faiss IndexFlatIP exact top-10 for 1,000 held-out query vectors; recall@10 of each candidate against it.
4. Candidates: numpy matmul; sqlite-vec vec0 float; vec0 int8; vec0 bit + float rescore (manual two-column and alpha rescore index); faiss Flat; usearch exact=True; usearch HNSW f16/i8 (M=16, ef_construction=128/200, ef_search sweep); hnswlib if it builds.
5. Metrics per candidate: p50/p95/p99 over >= 500 warm queries after 20 warm-ups (PLAN Appendix A), single-thread and default-thread; build/insert time for N; peak and steady working set sampled each second (include page cache effects: report both RSS and "cold file" first-query time); on-disk size; recall@10; DB-level behaviour: insert/supersede/delete cost and index rebuild time.
6. Also measure DRAM bandwidth (large memcpy/np.sum over 2 GB) to calibrate the section 5 model on the 225H, and run with the watchdog limits (<= 6 workers, free RAM > 12 GB).
7. Decision rule (written before running): keep flat if vector-stage p95 <= 40 ms (about 1/4 of the 150 ms stretch p95) at the largest realistic N (100k) AND recall@10 = 1.0. Adopt quantized flat if
   recall@10 >= 0.98 and strict end-to-end recall@5 on the dev split drops by < 1 point (paired bootstrap CI, 10,000 resamples) while p95 improves >= 30%. Adopt HNSW only if flat p95 > budget at N <= 2x projected corpus.

## 9. Limitations and conflicts (summary)
- No primary source measured any candidate on Windows, Python 3.13, or this CPU. All M-rows are on other hardware (M1 mini 8 GB; 2018 Xeon; 2019 Xeon + SSD) and different dims/datasets; they are 2018-2024 vintage.
- The sqlite-vec benchmark is the author's own, on v0.1.0 (2024), with a caveat that it is skewed to brute force; the stable code has changed (0.1.9) and the figure data for dims 384-1024 at 100k was not extractable.
- usearch-vs-faiss exact-search: README (20x faster) conflicts with the sqlite-vec author's measurement (usearch 56 ms vs faiss 10 ms on sift1m); no setup details for the README claim.
- Project-internal 46 ms / 860 ms figure conflicts with bandwidth physics by 1-3 orders of magnitude (see section 3); harness cost, not scan cost.
- hnswlib: README advertises 0.9.0/0.10.0-rc but PyPI stops at 0.8.0 (2023). conda-forge builds exist but add a second package manager.
- Quantization quality (M7) is for MTEB/English general retrieval, not short personal facts, and for specific models; our embedder may behave like nomic (87.7%) not mxbai (96.5%).
- Memory numbers exclude SQLite page cache, FTS5, Python runtime and the embedding model.

## 10. Verdicts
ADOPT: sqlite-vec 0.1.9 flat (vec0, float32) as the vector backend for <= 100k facts; keep the NumPy fallback; pin the version and keep the vector stage behind an interface.
ADOPT: faiss IndexFlat as an offline ground-truth tool inside the measurement harness only (not a runtime dependency).
TEST: int8 / bit + float rescore in sqlite-vec (manual two-column or alpha `rescore` index) - gated on recall@10 and strict end-to-end recall on our embedder.
TEST: usearch 2.26.5 (exact=True and HNSW with i8/f16) - only when measured flat p95 at the realistic N breaks budget, or if corpus projections exceed ~500k.
TEST: sqlite-vec 0.1.10 alpha ANN indexes (rescore first) - alpha, prerelease; evaluate in a sandbox DB only.
REJECT: hnswlib as a default (no Windows 3.13 wheel, PyPI stale, float32 only, second persistence layer).
REJECT: diskannpy / DiskANN for this project (no 3.12/3.13 wheel, billion-scale SSD design, legacy branch unmaintained); sqlite-vec DiskANN alpha not before an observed need.
REJECT: any HNSW/ANN index at <= 100k facts (adds recall loss and rebuild/delete complexity for a few ms saved, ESTIMATE).
