# R7: Temporal and contradiction handling in persistent agent memory

**Status:** Codex-authored evidence-based replacement after R7 exhausted four worker attempts without an acceptable package. This is a literature-backed design recommendation, not an experiment or implementation certification. Sources checked 2026-10-19.

## Executive recommendation

Use an append-only, provenance-preserving fact history with explicit temporal validity and supersession links. Build the current-state retrieval view from that history, and require a query to distinguish â€œcurrentâ€, â€œas of dateâ€, and â€œwhat changedâ€. A later timestamp alone must not win when the facts refer to different entities, scopes, sources, or validity intervals. Preserve unresolved conflicts and abstain when evidence does not establish which value applies.

Use explicit user corrections and trusted authoritative sources to supersede an active fact. Treat a retraction as a distinct state transition with actor, time, reason/source, and audit record; hide the retracted content from ordinary retrieval. Define deletion and retention behavior separately for logical retraction and legally/operationally required physical erasure.

The evidence supports testing these invariants. It does not establish a universal â€œbestâ€ supersession algorithm or a numeric gain from bitemporal storage. No local tests or latency measurements were run for this report.

## Evidence and scope

### Benchmarks and temporal reasoning

- LongMemEval defines five long-term interactive memory abilities, including temporal reasoning and knowledge updates, in a 500-question chat-assistant benchmark. It is useful for question answering over conversation histories but does not, by itself, establish correct write-time conflict handling or deletion semantics. [Paper](https://arxiv.org/abs/2410.10813), [official repository](https://github.com/xiaowu0162/LongMemEval).
- MemoryAgentBench identifies accurate retrieval, test-time learning, long-range understanding, and selective forgetting as four competencies. It turns long-context data into incremental multi-turn interactions and adds constructed datasets. This makes update/forgetting behavior more visible than a static retrieval test, but results remain tied to its tasks, memory systems, and answerer. [Paper](https://arxiv.org/abs/2507.05257).
- TReMu introduces temporal reasoning questions over multi-session dialogues by augmenting LoCoMo conversations. Its proposed system summarizes session timelines and uses code for date arithmetic. This supports testing explicit temporal questions separately from general recall; it does not demonstrate that the same method resolves arbitrary contradictory user facts. [ACL Anthology paper](https://aclanthology.org/2025.findings-acl.972/).
- Memora (April 2026 preprint) studies weeks-to-months personalized conversations and memory updates through remembering, reasoning, and recommending tasks. It motivates testing memory as it evolves over time, but should be treated as a preprint and its scores as benchmark-specific. [Paper](https://arxiv.org/abs/2604.20006).

### Shared-memory governance

- â€œGoverned Shared Memory for Multi-Agent LLM Systemsâ€ (arXiv:2606.24535v1, 2026-06-23) defines scope, provenance, propagation, and temporal supersession as system-level concerns. Its live evaluation reports one production service, not a comparison against a baseline. It reports 50 depth-four provenance chains reconstructed, and also identifies two important failures: a sub-tenant scope gap on direct GET-by-id (remediated during the study), and a synchronous near-duplicate filter that can reject a contradictory write before an asynchronous contradiction detector sees it. These are author-reported measurements in a single-system preprint, not independent effect sizes. [Paper and full evaluation](https://arxiv.org/html/2606.24535).
- The same paper's measured pipeline-ordering issue is relevant here: contradiction evidence must be considered before a deduplication gate can suppress a write. A semantic â€œlooks similarâ€ rule must not silently discard a new, incompatible value.
- The worker draft claimed 40% gains, 30â€“50% memory savings, and thresholds such as similarity 0.85 without traceable primary evidence. Those estimates are not retained. No universal near-duplicate threshold or governance effect size is established by the sources above.

## Recommended data and update semantics

Store each asserted fact as a versioned event with at least:

| Field | Meaning |
|---|---|
| `fact_id` | Stable ID for the assertion/version |
| `subject`, `predicate`, `object` | Normalized key and value, retaining original text |
| `scope` | User/project/agent/tenant visibility boundary |
| `valid_from`, `valid_to` | When the assertion is claimed to hold in the world; open-ended `valid_to` means current candidate |
| `recorded_at` | When this system learned/stored the assertion |
| `source_ref`, `source_type`, `actor` | Provenance and write authority |
| `status` | Active, superseded, retracted, or disputed |
| `supersedes_id` / `conflicts_with` | Explicit causal/history relationship; permit multiple conflicts |

This is a recommendation, not a claim that every field is already supported by the current schema. Keep original evidence and correction events so history can be reconstructed. Do not overwrite a fact in place or infer `valid_from` from `recorded_at` unless the source says they are the same.

For an explicit correction to the same entity/key/scope, atomically add the new version and mark the old one superseded. Preserve the old version for historical questions, but exclude it from default current-state answers. If the new statement is compatible, store both or merge only when the merge is evidence-preserving. If two claims conflict and authority, entity, scope, or validity cannot be resolved, mark both disputed and answer with the conflict or abstain.

Use source authority as a scoped rule, not a global numeric trust score. A direct user correction is authoritative for that user's preference; a timestamped system observation may be authoritative for machine state; an inferred model summary is weaker than its underlying source. Provenance must survive summarization and retrieval.

Near-duplicate handling should be downstream of key/entity and contradiction checks. Deduplication may merge exact duplicates with identical provenance/meaning, but must never discard a conflicting candidate solely because its embedding is similar. Any threshold is a local, labeled precision/recall parameter, not a literature constant.

Retractions should remove content from ordinary retrieval immediately while preserving the minimal audit event needed to prove the transition. The product must state what physical deletion means for backups, derived summaries, indexes, and logs; this policy has legal and privacy implications that the cited studies do not resolve.

## Query-time rules

1. Parse temporal intent: current state, a date/interval, chronology, or â€œwhat changedâ€. If parsing is ambiguous, ask for clarification at product runtime or return the ambiguity; do not silently choose current state.
2. Resolve entity and scope before ranking. A semantically close fact for another person, project, agent, or tenant is ineligible.
3. For current-state queries, filter superseded and retracted versions before semantic ranking. For historical questions, query by valid time and retain recorded-time provenance.
4. If multiple active incompatible values remain for one key, return a conflict with sources/times or abstain; do not rely on vector score or last-writer-wins alone.
5. Return source, actor, recorded time, valid interval, and supersession status with each selected fact so the answerer can cite the correct version.
6. Treat wall-clock changes, equal timestamps, timezone offsets, and future-dated inputs as explicit edge cases. Use a monotonic sequence or transaction order for event ordering; keep world-valid time separate.

## ForgetEval-style project test proposal

Use synthetic, hand-labeled fixtures first; keep this suite distinct from the existing golden set and the SEALED set. Each scenario is replayed as ordered write events and queried in current and historical modes. Pre-register the expected answers and source IDs before running the pipeline.

| Case | Setup | Required result |
|---|---|---|
| Explicit preference change | User says vegetarian, later explicitly says no longer vegetarian | Current query selects new value; prior-date query returns old value; both versions and source links remain |
| Non-conflicting detail | User adds a second preference | Both facts remain active; no false supersession |
| Entity collision | Same key/value for two people or projects | Scope/entity isolation; no cross-entity answer |
| Source disagreement | User report conflicts with a tool observation | Preserve both, apply declared authority only if the policy explicitly covers that key; otherwise dispute/abstain |
| Stale update | Old event ingested after a newer correction | Current state must not regress solely because ingestion time is later |
| Same timestamp / clock rollback | Equal timestamps and wall-clock moves backward | Deterministic order from event sequence; valid-time answers remain correct |
| Retraction | User requests a fact be forgotten | No ordinary query returns its content; audit records the request and deletion workflow |
| Near duplicate contradiction | Two similar embeddings encode opposite values | New write is not dropped by a duplicate gate; conflict is surfaced |
| Temporal interval | Fact valid only between dates | Current/out-of-interval query excludes it; as-of query includes it |
| Provenance chain | Derived summary points to source fact, then source is superseded | Summary is refreshed or marked stale; original source chain remains inspectable |
| Cross-agent scope | Private fact written by agent A, queried by B | B receives no content or identifying metadata unless policy grants access |
| Multi-write race | Two concurrent conflicting writes | One atomic, deterministic state transition; no two-current-value invariant violation without explicit disputed status |

Report exact counts for: current-state accuracy, historical accuracy, stale-fact leakage, false supersession, missed supersession, unresolved conflict surfaced, retraction success, provenance completeness, and unauthorized disclosure. Include per-case errors and 95% bootstrap confidence intervals where a sample-based aggregate is meaningful. For zero-event security failures, report numerator/denominator rather than implying a broad zero-risk guarantee.

Separate deterministic lifecycle checks from LLM question answering. For LLM tests, freeze the answerer model and prompt across all conditions, record the exact model per row, and judge claim-level support against the event fixture. A judge score is not a substitute for checking the deterministic active-version invariant.

## Experiment plan for this repository

**Hypothesis:** adding explicit valid-time and supersession-aware retrieval reduces stale-fact leakage and improves current/historical answer correctness versus the current accepted pipeline, without increasing false supersession.

**Conditions:** (A) current frozen pipeline; (B) same pipeline with explicit temporal/supersession filtering; optionally (C) a separately preregistered source-authority rule. No condition changes the answerer model.

**Data:** 120 labeled contradiction/update pairs for development and a distinct 60-pair held-out set, as specified in the existing plan. Include the cases above, balanced over explicit correction, compatible additions, ambiguous conflict, and delayed/stale ingestion. Keep SEALED inaccessible until the final once-only scoring phase.

**Metrics:** stale-fact leakage rate, current answer accuracy, historical answer accuracy, false and missed supersession, conflict/abstention precision and recall, retrieval latency, and write-path latency. Report exact denominators and paired 95% bootstrap intervals; use paired resampling at the scenario level.

**Decision rule:** adopt only if held-out stale leakage is zero in the fixture tests, the paired interval supports an improvement in the preregistered primary correctness metric, false supersession does not worsen beyond its interval, and latency remains within the project's gate. Otherwise keep the simpler behavior and report the unresolved cases. This rule is proposed before any run; no result is claimed here.

**Cost:** storage/index cost should be measured locally; schema fields and a status filter are expected to be small relative to model inference, but that expectation is not measured evidence. Do not extrapolate the single-service propagation latency in the cited preprint to this local SQLite/MCP system.

## ADOPT / TEST / REJECT

- **ADOPT (design invariant):** preserve fact provenance/history; represent explicit supersession and retraction as events; filter superseded/retracted facts from current retrieval; scope-check every read path; surface unresolved conflicts. These are correctness and audit requirements, not claims of benchmark gains.
- **TEST:** valid-time plus recorded-time fields; authority-aware conflict rules; near-duplicate thresholds; timeline summarization; temporal code/tool reasoning; propagation semantics if the store becomes multi-process or multi-agent. Test against labeled dev/held-out fixtures with stale leakage and false supersession measured separately.
- **REJECT:** unconditional last-writer-wins; destructive overwrite that erases history; embedding similarity as the sole duplicate/supersession rule; global trust scores that ignore source scope; silently selecting one of multiple incompatible active values; claims of universal performance gains without a local controlled evaluation.

## Limitations

- This report does not establish a production-ready temporal schema, prove current code behavior, or report local experiment results.
- MemoryAgentBench, TReMu, and Memora evaluate related but different tasks; none alone certifies the lifecycle and access-control invariants listed here.
- The 2026 governed-shared-memory source is an arXiv preprint and an author-associated single-system evaluation without a baseline comparison. Its measurements are not independent evidence of comparative efficacy.
- Legal deletion, retention, and backup policy require a product decision and cannot be inferred from these benchmark papers.
- All latency, RAM, accuracy, error-rate, and effect-size outcomes for this repository remain unknown until measured.
