## 1. Bottom line
1. Keep BM25 + dense. Fusion method matters less than having both; RRF (k=60) is a safe default but is NOT the best known fusion: Bruch et al. found a tuned convex combination beats it on 9/9 datasets.
2. With a labelled dev set of even a few hundred queries, a one-parameter score-normalized convex combination (min-max with a theoretical minimum) is the first challenger to RRF.
3. Exact identifiers (paths, versions, hashes, ids) are poorly served by embeddings and by word-tokenized BM25; the project should route them to an exact/trigram/prefix path. Evidence is mostly mechanism + vendor anecdote, not a controlled study, so the target (recall@1 = 1.00) must be proven on our own identifier subset.
4. LLM query rewriting / HyDE / multi-query: large gains reported only against weak retrievers on web-search benchmarks, and an independent 24-model study shows they usually HURT strong retrievers. Also add LLM latency to a 400 ms p95 budget. Default: do not ship; test gated.
5. Contextual retrieval: vendor-reported failure-rate reductions of 35%/49%/67% on its own mix of corpora; cost is paid at index time. Facts are short and atomic, so benefit is uncertain; test on the facts that contain unresolved references.

## 2. Fusion: RRF vs weighted vs score-normalized vs learned
Primary sources:
- Cormack, Clarke, Buettcher, "Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods", SIGIR 2009: https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf
- Bruch, Gai, Ingber, "An Analysis of Fusion Functions for Hybrid Retrieval", arXiv 2210.11934 (submitted 2022-10-21): https://arxiv.org/abs/2210.11934
- Elasticsearch RRF reference (default rank_constant = 60; each retriever equally weighted): https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion
RRF: score(d) = sum over rankings 1/(k + rank). Cormack: "k = 60 was fixed during a pilot investigation"; pilot MAP vs k for fusing 30 TREC systems on topics 351-400 (Table 1): k=0 .2072, 10 .2123, 30 .2139, 60 .2145, 80 .2147, 100 .2142, 500 .2098; best single system .2016, Condorcet .2074, CombMNZ .2039.
  So k is nearly flat from 30 to 100 in that setting. Final claim: RRF beat Condorcet 7/7 and CombMNZ 6/7 (sign test p ~ 0.008 / 0.04) over four TREC collections (Table 2, e.g. TREC Robust MAP .3686 vs best system .3586).
  CONFOUND for us: the fused inputs were up to 30 TREC participant systems (all lexical-era IR runs), not one BM25 + one embedding model; no hybrid text/dense evidence.
Bruch et al. setup (Section 3.2, Table 1): in-domain MS MARCO Passage v1 (8.8M passages, 6,980 dev queries), NQ (2.68M docs, 3,452 q), Quora (523K, 10,000 q); zero-shot BEIR NFCorpus (3.6K docs, 323 q), HotpotQA (5.23M, 7,405), FEVER (5.42M, 6,666), SciFact (5K, 300), DBPedia (4.63M, 400), FiQA (57K, 648).
  Lexical = PISA BM25 (k1=0.9, b=0.4, stemming, top 1000); semantic = all-MiniLM-L6-v2 (384-d, cosine). Metric NDCG@1000 (NDCG@100 for SciFact, NFCorpus), paired two-tailed t-test, p<0.01.
  Table 2 (NDCG; Lex / Sem / TM2C2 (alpha=0.8) / RRF(k=60)): MS MARCO .309/.441/.454/.425; NQ .382/.505/.542/.514; Quora .800/.889/.901/.877; NFCorpus .268/.296/.327/.312; HotpotQA .682/.520/.699/.675; FEVER .689/.558/.744/.721; SciFact .698/.681/.753/.730; DBPedia .415/.425/.512/.489; FiQA .315/.467/.496/.464. An oracle with per-query alpha reached e.g. .547 on MS MARCO (.637 NQ), showing large headroom for per-query weighting.
  TM2C2 = convex combination alpha*sem + (1-alpha)*lex after min-max with theoretical minimum for each score. Authors' findings: RRF is sensitive to k; Table 3: RRF(5,5) beats RRF(60,60) on most sets but RRF(10,4) collapses on HotpotQA (.621) and FEVER (.649);
  alpha tuned on in-domain validation transferred to all zero-shot sets; alpha converges with < 5% of the training queries (Fig. 12; averaged over 5 trials).
  Reading: lexical and semantic were within a few NDCG points of each other on most sets, so fusion helps; the margin of TM2C2 over RRF is 0.02-0.04 NDCG (~3-8% relative), not huge, but consistent.
  CONFLICT: Cormack et al. and Elasticsearch (rank-only, no tuning, robust) vs Bruch et al. (tuned convex wins). The two are compatible: RRF needs no labels; CC needs a few hundred labelled queries and a stable score distribution.
  CONFOUNDS: alpha=0.8 was tuned on the validation splits of the in-domain sets, i.e. a supervised advantage over untuned RRF(60); large web corpora, not 10k-100k short facts; one embedder; with a much stronger embedder or tiny corpora the weights shift. No confidence intervals on the aggregate except through t-tests.
Learned fusion (small model over rank/score/features): no primary evidence found for tiny personal-memory sets. Cormack's abstract mentions RRF as input to a LETOR 3 meta-learner (abstract-only for that claim). Risk: with a few hundred labelled queries a multi-feature model overfits; one-parameter CC is the sample-efficient middle (Bruch Fig. 12). Treat learned fusion as TEST-last.
Weighted RRF (per-retriever weights) is a hybrid of both; Bruch's RRF-CC variant (their Eq. 10) is the same idea. Cost of all fusion variants: microseconds on top-50 lists; no RAM concern.

## 3. BM25 and parameters
- SQLite FTS5 bm25() hard-codes k1 = 1.2, b = 0.75 and only accepts per-column weights (https://www.sqlite.org/fts5.html section 5.1.1). So k1/b tuning needs a different engine or a post-hoc rescoring from FTS5 candidates.
- Other defaults in the wild: Bruch et al. used k1=0.9, b=0.4; bm25s 0.3.14 (2026-10-18) defaults to k1=1.5 with the Lucene variant and notes the textbook range k1 1.2-2.0, b=0.75 (https://github.com/xhluca/bm25s). Three plausible defaults disagree, which is itself the finding: the optimum is corpus dependent.
- bm25s throughput table (single-thread Xeon 2.70 GHz, Kaggle; BEIR sets; README): e.g. scifact 952.92 q/s, nfcorpus 1196 q/s, msmarco 12.2 q/s. Shows pure-Python/NumPy BM25 is not a latency problem at <= 100k docs; but FTS5 is already in-process and 7.5 ms p50 per PLAN.
- For atomic one-sentence facts, length normalization (b) is the sensitive knob (all docs short, variance in length is informative or noise). No primary study on this; it is an ablation (A2).
- BEIR (arXiv 2104.08663, abstract-only): BM25 is a robust zero-shot baseline; dense models often underperform it out of domain. Supports keeping BM25 in the mix.
- Tokenizer matters more than k1/b for identifiers: FTS5 unicode61 treats every non-alphanumeric as a separator, so "v1.2.3", "C:\\Users\\x\\a.py", "src/foo_bar.ts" split into pieces; `tokenchars '-_'`/`separators` options exist (same page, 4.3.1).

## 4. Identifier handling: exact lookup, prefix, trigram
Primary source: SQLite FTS5 docs https://www.sqlite.org/fts5.html (sections 3.3 prefix queries, 4.2 prefix indexes, 4.3.4 trigram tokenizer); SQLite changes page: trigram added in 3.34.0 (2020-12-01); current SQLite is 3.54.1 (2026-10-16).
- Prefix: `abc*` works by range scan; `prefix='2 3'` option builds prefix indexes for 2/3-char prefixes to speed it. Good for version/path stems ("src/mem*").
- Trigram tokenizer: substring matching of any sequence >= 3 characters; also indexes LIKE/GLOB; case_sensitive option (1 allows only GLOB). Docs state: substrings < 3 characters match nothing in MATCH queries; a LIKE/GLOB with no 3+ non-wildcard run falls back to a linear scan; detail=none/column shrinks the index but limits tokens > 3 chars for MATCH.
  Implication: version strings like "1.2" (3 chars) work; "v2" does not via trigram; two-char ids need a plain indexed column equality.
- Index cost: no primary measurement found for trigram index size on short text. Mechanism: roughly one entry per character position, so the FTS5 trigram table is several times larger than a word index for path-heavy text. ESTIMATE only; measure DB size at 50k facts.
- Exact column: extract identifier-like tokens at ingest (regex for paths, semver, git SHA 7-40 hex, UUID, CVE-YYYY-N, ENV_VAR, file:line), normalize (case, slashes), store in a normalized table with a B-tree index on (identifier) -> fact id. Query side runs the same extractor; exact hits are inserted ahead of fused results (or fused with a high weight). Zero ML cost; microsecond lookup.
- Evidence quality: Anthropic's post gives the motivating example (query "Error code TS-999" where embeddings find general error-code content but may miss the exact string while BM25 matches it) https://www.anthropic.com/news/contextual-retrieval (2024-09-19) - an illustration, not a measured result. No controlled paper found that quantifies an identifier fast path versus RRF. So the 1.00 recall@1 stretch target must be established by A3 below.
- Confound to design around: exact-match boost can introduce false positives when an identifier appears in many facts (e.g. a repo path mentioned in 400 facts) - recall@1 is then ambiguous; the decision metric must be strict gold-id based (PLAN Appendix A).

## 5. Query rewriting, HyDE, multi-query
HyDE - Gao et al., arXiv 2212.10496 (2022-12-20): instruct LLM (InstructGPT text-davinci-003, temperature 0.7) to write a hypothetical document, embed with unsupervised Contriever, retrieve real docs. Setup: TREC DL19/DL20 (MS MARCO) and six BEIR low-resource sets.
  Table 1 (DL19 nDCG@10 / DL20 nDCG@10): BM25 50.6/48.0; Contriever 44.5/42.1; HyDE 61.3/57.9; fine-tuned ContrieverFT 62.1/63.2. Table 2 (BEIR nDCG@10: SciFact, ArguAna, TREC-COVID, FiQA, DBPedia, TREC-NEWS): BM25 67.9/39.7/59.5/23.6/31.8/39.5; Contriever 64.9/37.9/27.3/24.5/29.2/34.8; HyDE 69.1/46.6/59.3/27.3/36.8/44.0.
  Note TREC-COVID: HyDE 59.3 vs BM25 59.5 (no gain over BM25). Gains are largest relative to a weak unsupervised dense baseline; vs BM25 they are mixed and ~2-7 nDCG points.
Query2doc - Wang et al., arXiv 2303.07678 (2023-03-14): few-shot LLM pseudo-document appended to the query. Table 1: BM25 MS MARCO dev MRR@10 18.4 -> 21.4; DL19 nDCG@10 51.2 -> 66.2; DL20 47.7 -> 62.9. For strong supervised dense: SimLM DL19 71.4 -> 72.9 (+1.5), E5-base-KD 74.3 -> 74.9 (+0.6), MS MARCO dev MRR@10 +0.4/+0.8. Gains shrink as the retriever gets stronger.
Jagerman et al., arXiv 2305.03653 (2023-05-05): prompts (Q2D, CoT, PRF variants) with Flan-T5/UL2; MS MARCO dev with BM25 baseline: Recall@1K 87.82, MRR@10 18.77, nDCG@10 23.44; best Q2D/PRF (Flan-T5-XXL) MRR@10 22.13, nDCG@10 26.43 (Table 1, significant at p<0.01). On BEIR classic PRF stays strong for academic sets (trec-covid, scidocs, touche); LLM expansion helps QA-style sets (fiqa, hotpotqa, nq). Confirms "depends on domain and LLM knowledge".
Weller et al., "When do Generative Query and Document Expansions Fail?", arXiv 2309.08541 (2023-09-15): 11 expansion techniques x 12 datasets x 24 retrieval models, gpt-3.5-turbo expansions, rerank-setting (top 100 from BM25). Headline: strong negative correlation between base nDCG@10 and gain; Table 1 (DL19 / FiQA / ArguAna, QE delta): BM25 51.2 -4.0 / 23.6 +4.5 / 30.0 -5.4; E5-base-v2 67.3 -3.4 / 37.8 -0.6 / 51.1 -8.4; GTE-large 70.0 -4.5 / 41.2 -2.0 / 56.8 -8.8; MonoT5-3B 71.7 -2.8 / 45.9 -3.8 / 42.4 +6.8. Authors' recipe: use expansion for weak models or heavy domain shift, otherwise avoid.
  CONFLICT: HyDE / Query2doc report big wins (BM25 +15 nDCG on DL19 with query2doc) vs Weller reports query expansion lowers BM25 by 4.0 on DL19. Resolution candidates (hypotheses, not proven): different LLMs (davinci-003 vs gpt-3.5-turbo), prompt, whether expansions are appended vs used alone, PRF-style vs zero-shot, reranking-of-BM25-top-100 setting vs full retrieval, and BM25 implementation (51.2 vs 50.6 baseline). Also the MS MARCO / Wikipedia knowledge is likely memorized by the LLM (leakage), which flatters MS MARCO-derived sets and cannot help with private facts that no LLM has seen.
  The most important CONFOUND for our use: personal/project facts are NOT in the LLM's training data, so HyDE-style "LLM knowledge" cannot add facts; it can only add vocabulary/format paraphrase. Corpus-steered variants (CSQE, arXiv 2402.18031, abstract-only) were proposed precisely for that limitation.
Multi-query: RAG-Fusion (arXiv 2402.03367, 2024-01-31) is one company's chatbot with manual scoring of accuracy/relevance/comprehensiveness, no recall metric, no CI: weak evidence, and it notes drift when generated queries are off-topic. 2406.18960 (multi-query rewriting for conversational passage retrieval) is a different task (coreference in dialogue); abstract-only. Blended RAG 2404.07220 (hybrid query strategies, NQ/TREC-COVID/SQuAD) is abstract-only. No primary evidence for small private fact stores.
Latency (arithmetic, not measured): generating a 60-token rewrite at an assumed 20-60 tokens/s costs 1-3 s, far above the 400 ms p95 budget; cached/offline or gated-on-low-confidence use only. The measured rate of the actual local model must replace the assumption.
Deterministic query normalization (lowercasing, stop-phrase removal, identifier extraction, splitting "A and B" questions) has no LLM cost and is a separate, cheaper arm.

## 6. Contextual retrieval
Primary source: Anthropic, "Introducing Contextual Retrieval", 2024-09-19, https://www.anthropic.com/news/contextual-retrieval (vendor-run; no raw data or CIs on the page).
- Method: an LLM writes 50-100 tokens of chunk-specific context, prepended before embedding and before the BM25 index (so both are contextual).
- Setup stated: domains = codebases, fiction, ArXiv papers, science papers; top-performing embedder Gemini Text 004; metric 1 - recall@20 (failed retrievals in top 20 chunks); corpus/chunk counts not given on the page.
- Results (average failure rate): baseline 5.7%; contextual embeddings 3.7% (-35%); + contextual BM25 2.9% (-49%); + reranking 1.9% (-67%). The text says embeddings+BM25 beats embeddings alone, and top-20 beats top-10/top-5.
- Cost claim: $1.02 per million document tokens, assuming 800-token chunks, 8k-token documents, 50-token instruction, 100 tokens of context per chunk, using Claude with prompt caching. Local-model equivalent is NOT measured. Parametric arithmetic: generated tokens = N_facts x ctx_tokens; for 50,000 facts x 60 tokens = 3.0M tokens; time = 3.0M / rate; at an ASSUMED 35 tokens/s that is ~24 h, at 100 tok/s ~8.3 h, at 400 tok/s ~2.1 h. Prefill of the source document per fact is extra (cacheable). Real rate must be measured before E2 is scheduled, and the work belongs to an API worker or a nightly job, not the heavy-local window.
- The same post says a knowledge base < 200,000 tokens can just be placed in the prompt (no RAG). Our fact store of 10k+ facts is likely above that for 50k-fact scale (50k x ~30 tokens ~ 1.5M tokens, ESTIMATE), so not applicable as a replacement.
- Related alternative, no LLM generation: Late Chunking (Jina, arXiv 2409.04701, 2024-09-07) embeds the whole text with a long-context model then pools per chunk. Table 2 nDCG@10 averaged over SciFact, NFCorpus, FiQA, TREC-COVID and 3 models: fixed-size 256-token naive 52.2 vs late 54.0; sentence-boundary naive 52.4 vs late 54.3 (+3.6% rel.); per-dataset gains range 0 to +6.5 (NFCorpus J2s 23.5 -> 30.0), nomic-embed-text-v1 on SciFact 70.7 vs 70.6 (no gain). Requires a long-context embedder and token-level access (not available through a plain Ollama /embed call); the paper's chunked docs are long.
- Why uncertain for facts: contextual retrieval was designed for chunks cut from long documents. Our retrievable unit is already a short atomic fact, so the context may only help for facts with unresolved referents ("it", "the repo", "this version") or terse notes. The gain on already self-contained facts is likely small, while index time and index size (longer text embedded and in FTS) grow. Hypothesis only.
- CONFOUND: the 67% figure includes a reranker; the 35%/49% figures are the retrieval-only ones. Our pipeline already has a gated reranker, so the marginal gain vs "contextual + reranker" baseline may be lower.

## 7. Evidence-quality ranking (best to worst for OUR decision)
1. Highest: Bruch et al. (peer-reviewed-style analysis, public datasets, tables, significance tests) and Weller et al. (24 models, 12 datasets, tables): relevant to fusion and expansion decisions, but web/academic corpora.
2. Medium: Cormack 2009 (sign tests, classic TREC); Jagerman, HyDE, Query2doc (tables, single LLM family, mostly MS MARCO/BEIR); Late Chunking (tables, but different technique).
3. Low: Anthropic contextual retrieval (vendor, no counts, no CI, averaged across undisclosed corpora); SQLite docs are authoritative for mechanism but not for retrieval quality; RAG-Fusion (manual scoring, one company).
4. None found: identifier fast-path vs RRF on short facts; BM25 k1/b for atomic facts; any technique measured on personal memory stores.
General confounds across the literature: (a) baseline strength (stronger retriever -> smaller/negative gain); (b) benchmark contamination of LLMs on MS MARCO/Wikipedia; (c) metric and cut-off differences (NDCG@1000 vs @10 vs recall@20) make cross-paper numbers non-comparable; (d) BM25 implementations differ (51.2 vs 50.6 on DL19); (e) vendor runs; (f) no per-query CIs in most posts.
Confounds in OUR future evaluation: if gold questions were LLM-generated from the fact text, they overlap lexically with the fact and inflate BM25 and deflate the value of rewriting/HyDE (and conversely paraphrase-heavy human queries would favor dense/rewriting). Check provenance of the query set before interpreting A4-A6. Also the dev/held-out split discipline: tune alpha/k/b only on dev; report on held-out once.

## 8. Concrete ablation specs
Common rules (from PLAN-24H.md Appendix A and section 2.x): strict relevance; primary metric strict recall@5 with MRR secondary; bootstrap 95% CI (10,000 resamples) and paired bootstrap or McNemar; Holm correction over the ablations run on the same split; guard metrics = warm p95 latency, RAM, index-time minutes. Decision rule written before running.
Sample-size arithmetic (McNemar approximation, alpha 0.05 two-sided, power 80%; n = ((1.96*sqrt(p_d) + 0.84*sqrt(p_d - d^2)) / d)^2 where p_d = fraction of queries on which A and B disagree on hit/miss and d = true accuracy difference): p_d=0.10,d=0.05 -> ~311 queries; p_d=0.08,d=0.03 -> ~695; p_d=0.15,d=0.05 -> ~468. ESTIMATE: if the dev set has fewer than ~300 queries, only differences >= 5 points are detectable; say so instead of declaring ties as wins/losses.
A1 Fusion (E4). Hypothesis: a tuned score-normalized convex combination (min-max using the theoretical minimum score and the observed max of the candidate list, as in Bruch's TM2C2; cosine mapped to [0,1]) beats RRF k=60 by >= 2 recall@5 points. Arms: RRF k in {10,30,60,100}; weighted RRF; CC alpha grid 0..1 step 0.1 (alpha chosen by 5-fold CV on dev); per-query-type alpha (identifier / natural-language / mixed). Metric: strict recall@5, MRR, nDCG@10. Split: tune on dev, one confirmation on held-out. Cost: negligible latency (< 1 ms), 0 MB, ~30 min. Decision: adopt a challenger only if paired-bootstrap lower CI bound of (challenger - RRF60) > 0 on dev AND point difference >= +1.5 points on held-out; else keep RRF(60). Oracle-alpha upper bound reported to size remaining headroom (Bruch showed large oracle gaps).
A2 BM25 parameters and tokenization. Hypothesis: for short facts, lower b (0.3-0.5) and tokenchars preserving '-_./' improve recall@5 over FTS5 defaults (k1 1.2, b 0.75). Arms: FTS5 default; FTS5 unicode61 tokenchars '-_.'; bm25s/rank_bm25 candidate rescoring with k1 in {0.9,1.2,1.5,2.0} x b in {0.3,0.4,0.75}; porter stemming on/off. Metric: strict recall@5 for the BM25-only retriever and for the fused system. Cost: index rebuild minutes; RAM unchanged (bm25s mmap option). Decision: adopt only if fused-system gain >= 1 point with CI > 0; otherwise keep FTS5 defaults (zero new dependency).
A3 Identifier fast path (E8). Hypothesis: exact + prefix + trigram lookup yields recall@1 >= 0.99 on the identifier subset (vs baseline measured) without lowering overall recall@5. Arms: baseline RRF; + exact normalized-identifier table boost; + FTS5 trigram table (case-insensitive) for substring/path fragments >= 3 chars; + prefix index prefix='2 3'. Metrics: recall@1 and MRR on identifier subset (primary); false-positive rate = fraction of non-identifier queries where an exact hit displaces the gold fact from rank 1 (guard, <= 0.5 point); DB size growth; ingest time per 1k facts. Split: stratified so every identifier type (path, semver, SHA, UUID, issue id, env var) has >= 20 queries or is reported as "underpowered". Cost: expected < 5 ms lookup; DB size to measure (trigram index likely several x the word index, ESTIMATE). Decision: adopt exact table if identifier recall@1 gain >= +5 points with CI > 0 and guard passes; add trigram only if exact table misses fragment queries (>= 20 queries show it) and size growth <= 2x DB.
A4 Query rewriting (E3), deterministic first. Hypothesis: deterministic normalization (strip chat boilerplate, extract entities/identifiers, split compound questions) gains >= 2 points at no LLM cost; LLM rewriting does not beat it. Arms: raw; deterministic normalization; LLM rewrite (local small model, single call, 1 sample, temp 0); both. Metric: recall@5, MRR, answer-containment; guard p95 latency. Cost: LLM arm adds measured generation time (assume 1-3 s until measured); run LLM arm only on a 300-query subset first. Decision: LLM rewriting adopted only if gain >= +3 points with CI > 0 AND added p95 < 150 ms (or applied only when first-pass confidence is below threshold and the extra latency is accepted by the owner). Otherwise REJECT.
A5 HyDE. Hypothesis (null-leaning, per Weller et al.): HyDE does not improve strict recall@5 over hybrid RRF and adds latency. Arms: hybrid baseline; dense query replaced by embedding of hypothetical fact (1 sample, 40 tokens); dense query = mean(query, hypothetical) embedding. Metric: recall@5, MRR on the natural-language (non-identifier) subset; also report on questions that need vocabulary bridging. Cost: one extra LLM call per query + one extra embedding; RAM unchanged. Decision: adopt only if >= +3 points on the NL subset with CI > 0 and p95 within budget; since LLM has no knowledge of private facts, expect REJECT.
A6 Multi-query. Hypothesis: 3 LLM paraphrases fused by RRF improve recall@5 on multi-aspect questions by >= 3 points but not on single-fact lookups. Arms: baseline; 3 paraphrases (RRF over 3+1 lists); decomposition into sub-questions. Metric: recall@5 on the multi-hop/aggregate subset and overall; guard latency (+3 embedding calls, +1 LLM call). Decision: run only if the dev set has >= 100 multi-aspect questions; adopt only if gain >= +3 on that subset with no overall regression > 0.5 point.
A7 Contextual retrieval (E2). Hypothesis: prepending 1-2 sentence generated context to facts that contain unresolved referents reduces failed recall@5 retrievals by >= 20% relative (vendor figure for embeddings only was 35%), with less gain on self-contained facts. Arms: baseline; context in embedding only; context in embedding + FTS (contextual BM25); contextual + existing reranker gate. Metric: 1 - recall@5 and recall@20 failure rates (to compare with vendor), strict recall@5, MRR; stratify facts by "contains pronoun/unresolved reference" (heuristic or judge-labelled). Cost: index time = N_facts x ctx_tokens / measured generation rate (e.g. 3.0M tokens for 50k x 60; hours, section 6), DB size +60 tokens/fact, p95 latency unchanged at query time. Run on a 5k-fact sample first (about 1/10 of the cost) and extrapolate. Decision: scale to full corpus only if sample gain >= +2 points recall@5 (CI > 0) and index time fits an overnight/API budget.
A8 Learned fusion. Hypothesis: gradient-boosted/logistic fusion over features (BM25 rank & score, cosine, identifier match, fact status/recency) beats best tuned CC by >= 2 points. Arms: best CC from A1; logistic regression; small GBDT, nested 5-fold CV with query-grouped folds (no query leakage). Cost: training seconds; features add < 2 ms. Run only if A1 shows per-query-type headroom and dev labelled queries >= 500. Decision: adopt only if nested-CV gain >= +2 points with CI > 0 and held-out confirms; else REJECT (overfit risk, Bruch Fig. 12 favors few-parameter models).

## 9. Limitations
- No local measurement; no corpus-specific evidence. All quantitative claims are from public benchmarks (MS MARCO, BEIR, TREC) with large web/academic documents, versus short personal facts.
- Discovery limited by missing search provider; I may have missed 2025-2026 papers on hybrid retrieval, learned sparse retrieval or agentic memory benchmarks. I did not read abstract-only papers' tables (2402.03367, 2406.18960, 2404.07220, 2402.18031, 2104.08663).
- The Anthropic numbers are vendor-reported, average over undisclosed corpus sizes, and the post has no raw data. Treat as direction not magnitude.
- Cormack's 2009 k=60 experiment fused lexical TREC systems, not text+dense; Elasticsearch default 60 shows adoption, not accuracy evidence.
- Latency/cost lines for LLM steps use assumed token rates and are labelled; real rates must be measured with the actual local model.
- Sample-size formula is a normal approximation; with discordance unknown it is a planning guide only.

## 10. Verdicts
